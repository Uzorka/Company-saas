# A login for every role

Five roles ship with the product. This is how to get a working sign-in for each
one, so every screen can be tested as the person who actually uses it.

**There are no passwords in this repository, and there will not be.** Test
credentials committed to a repository become production credentials the week
someone reuses them. You set every password yourself: two in the Supabase
dashboard, the rest generated by the product and shown to you once.

Budget about ten minutes.

---

## Before you start

Your database must be at migration 0033 or later. Run
`supabase/setup/install.sql` in the Supabase SQL editor — it is re-runnable and
skips what is already applied — then `supabase/setup/verify.sql` to confirm.
Without 0033 the Role grants screen will appear to work and then fail at the
last step.

If you want the workspace to have data in it, run `supabase/setup/demo-seed.sql`
too. It creates 23 fictional employees and no accounts.

---

## The roles

| Role | High risk | What they see | How the account is made |
|---|---|---|---|
| **Management** | Yes | Everything, including payroll figures and the audit log | Supabase dashboard (stage 1) |
| **HR** | Yes | People, hiring, documents. Not payroll figures | Role grant, two people (stage 3) |
| **Accounts** | Yes | Payroll, payslips, salary for everyone | Role grant, two people (stage 3) |
| **Head of Department** | No | Their department's people, tasks, attendance, leave | Create account (stage 2) |
| **Employee** | No | Their own record, tasks, leave, payslips | Create account (stage 2) |

The three high-risk roles carry payroll, document, settings or audit access. No
single person can grant one — that is enforced by a trigger on `user_roles`, not
by a screen, so it holds regardless of which route someone takes.

## Stage 1 — two Management accounts

**Two, not one.** Only Management holds `roles.manage`, and a high-risk grant
needs one person to request and a *different* person to approve. With a single
administrator you can never issue HR or Accounts at all.

This is the only stage that happens outside the product. It works because the
SQL editor carries no session — there is nobody yet who could be the second
approver, so the guard stands aside for exactly this case.

1. **Supabase dashboard → Authentication → Users → Add user.** Create two:

   | Suggested email | Who they are |
   |---|---|
   | `md@heron.test` | First administrator — the one you will use most |
   | `deputy@heron.test` | Second administrator — exists to approve grants |

   Tick **Auto Confirm User**. Set a password for each, right there. Use two
   different ones and keep them in your password manager.

2. **SQL editor** — find the ids:

   ```sql
   select id, email from auth.users order by created_at desc;
   ```

3. Run this **once for each** of the two ids:

   ```sql
   insert into organization_members (organization_id, user_id, status)
   values ('00000000-0000-4000-8000-000000000001', '<user-id>', 'active');

   insert into user_roles (organization_id, user_id, role_id)
   select '00000000-0000-4000-8000-000000000001', '<user-id>', id
   from roles
   where organization_id = '00000000-0000-4000-8000-000000000001'
     and slug = 'management';
   ```

4. Sign in at `/auth/login`. The workspace code is `chfheron` — the organisation's slug from `supabase/seed.sql`.

You now have **Management** working. Everything else is done inside the product.

## Stage 2 — Head of Department and Employee

Signed in as `md@heron.test`:

1. **Employees → Create account.**
2. Fill in name, email, and pick the role — **Head of Department** or
   **Employee**.
3. Optionally link the account to one of the demo staff records. Do this for at
   least one Employee account: without it, every "my own" screen is legitimately
   empty — no payslip, no leave balance, no assigned tasks — because the
   policies correctly match nothing.
4. **Copy the password before you close the panel.** It is generated at that
   moment, shown once, and never stored, logged or recoverable. The panel does
   not close by itself for exactly this reason. If you lose it, delete the user
   in the Supabase dashboard and start again.

Repeat for both roles.

| Suggested email | Role | Link to employee |
|---|---|---|
| `hod@heron.test` | Head of Department | A staff record in Sales |
| `staff@heron.test` | Employee | Any staff record |

The high-risk roles are deliberately absent from that form. Choosing one is not
an error you can make.

## Stage 3 — HR and Accounts

These take two people. Make the account first, then raise its role.

**a. Create the account** — Employees → Create account, role **Employee**,
email `hr@heron.test`. Copy the password.

**b. Request the role**, still as `md@heron.test`:

Settings → **Role grants** → *Request a role*. Choose the person, choose **HR**,
and write why. The reason is kept permanently and is read by whoever approves
it, so write the real one. At least a sentence.

Nothing is granted yet. The request shows as *Awaiting approval*, and the
approve buttons are not offered to you — you raised it.

**c. Approve it as the other administrator.** Sign out, sign in as
`deputy@heron.test`, go to Settings → Role grants, and choose **Approve and
grant**.

**d. The new HR signs out and back in.** Claims are stamped into the token at
sign-in, so an open session will not see the new role.

Repeat for **Accounts** with `accounts@heron.test`.

## Worth testing, once you have them

These are the places where the roles actually differ, and where a mistake would
be expensive:

- **Payroll figures.** Sign in as HR and open Payroll. HR owns people data and
  cannot see what anyone is paid — the page should say so, not show zeroes.
- **Another department.** As `hod@heron.test`, search the directory for someone
  outside their department. They are not hidden by a filter; the row does not
  exist as far as that session is concerned.
- **Your own payslip.** As `staff@heron.test`, Payslips shows theirs and only
  theirs — provided you linked the account to an employee record in stage 2.
- **The audit log.** As Management, Audit shows who granted what, including the
  role grants you just made. Nobody can edit it, including you.
- **Approving your own request.** As `md@heron.test`, raise a grant and try to
  approve it. The buttons are not there — and if they were, the database would
  refuse it.

## If something does not work

**A new role does not appear.** Sign out and back in. Claims are stamped at
sign-in.

**"Granting … needs an approved request with a second approver."** Migration
0033 doing its job — the role was written directly rather than through Role
grants. Use Settings → Role grants.

**The approve buttons are missing.** You are the requester. A different
administrator has to approve it.

**Create account is missing from Employees.** It needs both `employees.create`
and `roles.manage`, which in practice means Management.

**You lost a generated password.** It is not recoverable by design. Delete the
user in the Supabase dashboard and create the account again.
